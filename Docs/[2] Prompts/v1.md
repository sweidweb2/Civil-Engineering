You are working on an existing software project. Treat everything in this document as the current architectural baseline.

The primary goals are:

* Keep the system clean.
* Keep responsibilities clearly separated.

# 5. BACKEND LAYER RESPONSIBILITIES

## Routes

Routes define:

* HTTP method
* URL
* Middleware
* Controller endpoint

Routes should NOT contain business logic.

Example:

```text
POST /api/v1/projects
    ↓
ProjectController.create
```

---

## Controllers

Controllers are the HTTP/API boundary.

Controllers are responsible for:

* Receiving HTTP requests
* Reading params/body/query
* Calling validation
* Calling the appropriate service
* Returning HTTP responses
* Mapping application results to API responses

Controllers should remain thin.

Controllers should NOT contain:

* Complex business logic
* Database queries
* Prisma calls
* Large calculations
* Business workflows

Bad:

```text
Controller
    ↓
20 business rules
    ↓
Database query
```

Good:

```text
Controller
    ↓
Service
    ↓
Repository
```

---

## Services

Services contain application/business logic.

Services are responsible for:

* Business rules
* Application workflows
* Calculations
* Orchestration
* Calling repositories
* Coordinating multiple domain operations when appropriate

Services should NOT directly perform raw database access when that access belongs in a repository.

---

## Repositories

Repositories are responsible for data access.

They communicate with:

```text
Repository
    ↓
Prisma
    ↓
PostgreSQL
```

Repositories should NOT contain business workflows.

Example:

```text
projectRepository.findById()
projectRepository.create()
projectRepository.update()
```

The repository answers:

> How do I get/store this data?

The service answers:

> What should the application do?

# 6. DDD / DOMAIN ORGANIZATION

The backend should be organized by business domains/modules.

Example:

```text
backend/
└── src/
    └── modules/
        ├── auth/
        ├── users/
        ├── projects/
        ├── expenses/
        ├── workers/
        ├── materials/
        └── ...
```

Each module owns its related logic.

Example:

```text
projects/
├── project.routes.ts
├── project.controller.ts
├── project.service.ts
├── project.repository.ts
├── project.schema.ts
└── project.types.ts
```

Do not create huge global folders such as:

```text
controllers/
services/
repositories/
```

containing hundreds of unrelated files.

Prefer domain ownership.

# 7. DOMAIN BOUNDARIES

Each module should:

* Own its business logic.
* Own its relevant data-access logic.
* Have a clear responsibility.
* Avoid accessing another module's internal implementation directly.
* Communicate through clearly defined interfaces/services when necessary.

Avoid:

```text
Project module
    ↓
directly modifies
    ↓
internal database logic of Worker module
```

Prefer controlled communication.

Avoid circular dependencies between modules.

# 13. DATABASE RULES

Define and consistently use:

* Primary keys
* Foreign keys
* Relationships
* Unique constraints
* Indexes
* Nullable/non-nullable fields
* Timestamps
* Appropriate enums
* Transactions
* Referential integrity

Avoid unnecessary database queries.

Be aware of:

* N+1 queries
* Missing indexes
* Unnecessary joins
* Over-fetching
* Under-fetching

Use transactions when multiple related operations must succeed/fail together.

# 42. CORE DEVELOPMENT PHILOSOPHY

The project should always follow these principles:

### Simple

Prefer:

```text
Simple + clear
```

over:

```text
Complex + clever
```

### Clear

A developer should be able to understand:

* Where functionality lives.
* Who owns it.
* Which layer handles it.
* Which domain owns it.
* How data flows.

### Organized

Everything should have an obvious home.

### Separated

Each layer and module should have a clear responsibility.

### Reusable

Reuse actual shared behavior instead of duplicating it.

### Maintainable

Optimize for the future developer who must understand the code.

### Secure

Security is enforced by the backend and infrastructure, not by assumptions about the client.

### Practical

Do not introduce architecture merely because it is theoretically sophisticated.
